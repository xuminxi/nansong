# 南松推拿馆 · 线上预约小程序

简约新中式风格的按摩店预约小程序，含**用户端（4 个 Tab）**与**商家管理后台**。
本项目为**本地数据版**（数据存于手机缓存），无需服务器即可完整跑通预约全流程。

---

## 一、如何运行

1. 打开**微信开发者工具**，用微信扫码登录。
2. 首页选择 **「导入」→「导入项目」**（不要双击文件夹打开）。
3. 目录选择本文件夹 **`massage-miniprogram`**（其内含 `app.json`）：
   ```
   C:\Users\leng\WorkBuddy\2026-10-20-22-37-13\massage-miniprogram
   ```
4. AppID 一栏选择 **「测试号」**，点击导入，编译即可预览。

> 若导入报错，多半是选到了外层目录（没有 `app.json`），请确认路径到 `massage-miniprogram` 这一层。

## 三、用户端功能

### Tab 1 · 首页
轮播图、门店介绍、营业时间、双电话一键拨打、地址地图导航、技师团队展示、精选项目。

### Tab 2 · 项目
5 个项目：15 / 30 / 60 / 90 分钟按摩、30 分钟艾灸。
**点选项目后自动匹配「最近可约时段」**——两位技师都空闲时随机分配，只空闲一位则分配给该技师，均忙则顺延到下一个最近时段。

### Tab 3 · 技师
技师头像、简介、擅长项目；可展开查看**该技师今日空闲区间**（独立排班，互不干扰）；「约 TA」进入指定技师预约，**只显示 TA 的空闲时间**，手动自选时段。

### Tab 4 · 我的
- 微信授权登录（本地会话），填写一次手机号后预约自动带入。
- 预约记录按 全部 / 待确认 / 已到店 / 已完成 / 已取消 筛选，显示预约起止时间。
- 待确认的预约可自助取消。

### 预约规则
- **占用时长 = 项目时长**：选 90 分钟项目从 15:00 开始，即占用 15:00–16:30。
- **冲突校验**：同一技师已占用的区间不可再约；结束时间恰好等于下一单开始时间（如 11:00 接 10:00–11:00 的单）不算冲突。
- **不跨营业时间**：开始时间 + 项目时长不得晚于打烊时间 21:30，超出则该时段自动置灰。
- **两技师排班独立**：A 被预约不影响 B 在同一时段的接单。
- 无需支付，仅做预约登记。

## 六、重要说明

- **数据是本地的**：预约记录存在当前手机/模拟器缓存中，**不同设备之间不互通**，仅供单机演示或店内一台设备登记使用。
- 需要顾客在自己手机上预约、店家在另一台设备接单（跨设备同步），需接入云数据库。届时**只需替换 `utils/store.js` 一个文件**，页面层无需改动。
- 微信手机号一键获取（`getPhoneNumber`）需企业主体小程序并配合服务端解密，当前为「登录 + 手动填一次手机号自动带入」的等效方案。

## 七、接入服务端（跨设备同步 + 微信手机号）

当前默认是**本地数据版**（数据只在本机）。要做到「顾客在自己手机下单、店家在另一台设备接单」并拿到微信手机号，需要接入服务端。

### 前置条件（硬门槛）

| 事项 | 说明 |
|---|---|
| 小程序主体 | 必须是**已认证的非个人主体**（个体工商户即可，认证 30 元/年）。**个人主体永久拿不到微信手机号** |
| 接口权限 | 公众平台 → 开发 → 开发管理 → 接口设置 → 申请「获取手机号」 |
| 服务器 | 云服务器（2核2G 起） |
| 域名 + ICP 备案 | 国内服务器必须备案，7–20 天 |
| HTTPS | 免费证书 + Nginx 反代 |
| 域名白名单 | 开发 → 开发设置 → 服务器域名 → request 合法域名 |

> 只想做数据同步、不要手机号的话，个人主体也能跑，手机号仍手填。

### 已提供的代码

```
server/
├── config.js   AppID/AppSecret/后台密码（用环境变量注入）
├── db.js       JSON 单文件数据库（原子写入）
├── wx.js       code2Session + getPhoneNumber（官方 HTTPS 接口）
├── core.js     预约核心逻辑（时长占用制，与小程序端规则一致）
├── index.js    HTTP 服务（零依赖，node index.js 直接跑）
└── README.md   完整部署步骤
```

小程序端：
- `utils/api.js` —— 接口封装，改 `API_BASE` 为你的域名
- `utils/store.cloud.js` —— 云版数据层，**接口与 `utils/store.js` 完全相同**

### 切换方式

1. `utils/api.js` 里把 `API_BASE` 改成 `https://你的域名/api`
2. 把 `utils/store.cloud.js` 覆盖 `utils/store.js`（原文件建议备份为 `utils/store.local.js`）
3. 重新编译

页面层**无需任何改动**：云版数据层暴露了同名接口，并用 `asPromise` 兼容了「本地同步返回」与「服务端 Promise」两种形态。

### 手机号是怎么拿到的

```
用户点 <button open-type="getPhoneNumber">
   → 回调拿到 code（一次性、5 分钟有效）
   → 前端 POST /api/auth/phone
   → 服务端用 access_token 调
     POST https://api.weixin.qq.com/wxa/business/getuserphonenumber
   → 返回真实手机号，落库并回填给前端
```

`wx.login` 只能换 openid，拿不到任何用户信息或手机号；`wx.getUserProfile` 已被微信收回，只返回灰色头像和"微信用户"——这是平台限制，不是代码问题。

详细的部署命令、Nginx 配置、接口清单见 **`server/README.md`**。

## 八、如何防止虚假预约（风控）

**先说结论：手机号只是联系方式，不是身份证明。** 能填出 11 位数字不等于这个号存在、
更不等于这个人会来。真正可靠的身份锚点是 **openid**（一个微信号一个，微信官方保证唯一、
无法批量伪造）—— 它不需要手机号就能拿到（`wx.login` + 服务端 `code2Session`）。

因此本项目的防刷分三层：

### 第一层｜服务端风控（接入服务端后生效，主力）

见 `server/risk.js`，共 8 条规则（均可在商家后台调阈值）：

| 规则 | 默认 | 作用 |
|---|---|---|
| 号码合法性 | 开 | 拦截 `11111111111`、`12345678901` 等明显虚假号 |
| 下单冷却 | 60 秒 | 防脚本连点 |
| 未完成上限 | 2 单 | 同一微信号同时未完成的预约数 |
| 每日上限 | 4 单 | 同一微信号每天下单数（已取消不计） |
| 号码归属 | 开 | 一个手机号只能属于一个微信号，防冒用他人号码 |
| 号码占坑 | 1 单 | 同一手机号同时未完成订单数 |
| 爽约惩罚 | 3 次 | 累计爽约自动限制预约 |
| 黑名单 | — | 商家可按微信号或手机号手动拉黑/解除 |

### 第二层｜核销闭环（最能筛出真实顾客）

下单生成 **6 位核销码**，顾客在「我的 → 预约记录」可见，商家订单页也显示。
顾客到店报码 → 商家点「已到店」；没来 → 商家点「**未到店**」，该顾客爽约 +1，
累计 3 次自动限制。**真实顾客会到店，虚假预约不会**——这不依赖手机号验证。

### 第三层｜手机号授权（可选，最强但有门槛）

企业/个体工商户主体可申请「获取手机号」权限，用户点按钮即授权真实号码，
无法乱填。门槛：非个人主体 + 微信认证 + 服务端解密。详见 `server/README.md`。

### 本地数据版能做到什么

当前默认是本地版（数据在手机缓存里），**没有 openid**，只能以手机号为锚点做最基本的限制：
号码合法性校验、同一手机号未完成订单上限（2 单）、下单冷却（60 秒）。
参数在 `utils/store.js` 顶部的 `RISK_LIMIT`。要完整的 openid 级约束必须接入服务端。
